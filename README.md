# TRENZO MVP

Статическое Telegram Mini App: HTML, CSS и JavaScript. Кабинет спортсмена
использует существующие Supabase Edge Functions. Кабинет тренера — отдельный
frontend-прототип, доступный через обязательный выбор роли.

## Прототип тренера

Навигация: **Главная · Клиенты · Разборы · Схемы · Аналитика**.

- `screens/trainer-data.js` — единые демо-данные и действия над ними.
- `screens/trainer.js` — экраны, переиспользуемая разметка и навигация.
- `styles/trainer.css` — стили, ограниченные тренерским кабинетом.

Подтверждение разбора обновляет очередь и сохраняет решение в истории клиента.
Программы можно редактировать и назначать с отдельным подтверждением.
Профиль, решения и программы сохраняются локально в ключах
`trenzo-trainer-demo-v1:<Telegram ID или local>`. Реальные данные спортсменов
не читаются и не изменяются. AI и приглашения демонстрационные.

В **Профиль → Данные примера** можно загрузить обычный рабочий день, спокойный
день или пустой кабинет. Загрузка примера заменяет только демо-изменения.

Для локального просмотра: `python3 -m http.server 4173 --bind 127.0.0.1`.
Для проверки состояния и переходов: `node --test tests/trainer-state.test.cjs`.

При подключении backend заменять адаптер данных, сохраняя общий источник
профиля, питания, веса и тренировок спортсмена. Сервер должен проверять связь
тренера с клиентом; демо-назначения и локальный Telegram ID не дают доступ к БД.

## Недельные разборы

Разбор — отдельный обзор каждого клиента за семь календарных дней, не лента
единичных событий. День, время и IANA-часовой пояс задаются в профиле или через
«Разборы → Расписание». По умолчанию: воскресенье, 18:00, Europe/Moscow;
период — предыдущее воскресенье–суббота. До выбранного времени новая очередь
не создаётся. При открытии кабинета догружаются пропущенные недельные очереди.
Новый клиент включается начиная с недели его добавления, не задним числом.
Смена дня меняет будущие периоды и сохраняет архив; первый новый период может
пересекаться с предыдущим расписанием. Каждый период всегда содержит семь дат.

В карточке: даты, количество записанных тренировок относительно плана,
дни дневника питания и динамика сопоставимых упражнений. Сравниваются последние
выполнения в соседних периодах: тот же день программы, упражнение и число
подходов. Разнонаправленные изменения веса/повторов не выдаются за рост.
RPE — субъективная тяжесть, не повторения. Сон и вода не используются.

Внутри: текущий вес и вес на конец периода, датированные замеры, исторический
план и фактические подходы, питание с целями на начало периода, фото и видео,
решение на следующую неделю. Медиа отображается по HTTPS-ссылкам из
`client.mediaReports` (`type`, `recorded_on`, `url`, `caption`); клиентская
загрузка ещё не подключена. Автоматического анализа медиа нет.

История назначений `planHistory` сохраняет независимые копии программ.
При миграции старых демо-данных исторический план не восстанавливается из
текущего: показывается отсутствие данных. Завершение сохраняет снимок недельных
данных и решение в истории клиента, но не назначает программу автоматически.
Для изменения следующего плана доступен существующий конструктор программы.

**Это локальный frontend-MVP.** Для реальных разборов нужны серверная история
назначений, связь тренер–клиент, приватное хранилище медиа и планировщик Supabase
с уникальным ключом тренер/клиент/период. Фоновые Telegram-уведомления,
серверная генерация и загрузка фото/видео этим изменением не подключаются.
