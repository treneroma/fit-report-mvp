# Цикл отчётов: локальная демонстрация

Это рабочая демонстрация сценария, не передача между аккаунтами. Живой кабинет
спортсмена, его Supabase Edge Functions и Telegram-отправка не изменены.
Демо хранится в существующем ключе `trenzo-trainer-demo-v1:<identity>`.
При недоступном localStorage приложение предупреждает о временном хранении.

## Как проверить

1. Выбрать роль тренера → «Отчёты». На первом входе подготовлены четыре
   поступивших отчёта, ожидаемый, просроченный и три разобранных отчёта.
2. Вкладки: «К разбору», «Просрочили», «История». В просроченных только
   неотправленные отчёты с истёкшим сроком; обычные ожидания не показываются.
3. Открыть карточку: четыре показателя → состояние клиента, включая крепатуру →
   питание (план КБЖУ и семь дат) → раскрывающиеся тренировки с фактом и динамикой →
   наблюдения TRENZO → предложение следующего цикла.
4. В разделе «Предложение TRENZO» отдельно показаны тренировки и питание.
   Каждое упражнение содержит параметры и причину изменения или сохранения.
   Карандаш около каждой тренировки открывает только её поля; отдельный карандаш
   питания включает редактирование КБЖУ. Общая кнопка «Изменить» открывает все поля.
   Кнопка «Принять» сохраняет сделанные правки, не заменяя их исходным предложением.
5. Нажать «Сформировать ответ клиенту»: только после этого появляются
   согласованные тренировки, питание и необязательный комментарий тренера.
   Изменение плана сбрасывает сформированный ответ, сохраняя комментарий;
   требуется повторное формирование. Затем «Отправить клиенту». Сохраняется пакет
   `resolution.delivery`: тренировки, питание, комментарий клиента и тренера.
   Отчёт уходит в историю, badge уменьшается, решение попадает в память.
6. Перезагрузить приложение: черновики и история сохраняются. Клиентская форма
   пока проверяется автотестами; ссылка на неё из тренерского кабинета убрана.

Тестовые данные дополняют только локальных демонстрационных клиентов и не
перезаписывают существующие дневники. Для Александра подготовлено сравнение
RPE и сна. Демо-анализ — детерминированные правила `demo-rules-v1`, не AI-запрос
и не медицинское заключение. Голосовой ввод/распознавание пока не подключены.

## Файлы и границы ответственности

- `screens/report-cycle.js`: переходы состояний, вопросы, снимки, сравнения,
  рекомендации, валидация, закрытие и интерфейс адаптера; без DOM и HTTP.
- `screens/report-ui.js`: два интерфейса и изолированный демо-адаптер.
- `screens/trainer-data.js`: локальное сохранение; закрытие, следующий план и
  память записываются одним сохранением состояния.
- `styles/reports.css`: стили новых компонентов в существующей оболочке.
- `tests/report-cycle.test.cjs`: новые сценарии, включая делегированные обработчики.

Старые `weeklyReviews` не считаются отправленными отчётами клиента. Их данные
и решения не удаляются: старые ссылки из памяти продолжают открываться.

## Контракт данных v1

Один `period-report` на клиента и семь календарных дат. Локальный ID:
`period-report:<clientId>:<start>:<end>`.

- Основа: `version`, `kind`, `clientId`, `start`, `end`, `dueOn`, `dueTime`,
  `timeZone`, `createdAt`.
- До отправки: необязательный `clientDraft`.
- `submission`: `submittedAt`, проверенные `answers`, независимый `snapshot`
  фактов и `analysis` с версией правил. После отправки не переписывается.
- До ответа: `trainerDraft` с режимом решения, выбранными рекомендациями,
  следующим планом, черновиком ответа и признаком ручного редактирования ответа.
- `trainerDraft.weeklyPlan`: структурированный цикл со всеми упражнениями,
  параметрами, причинами и КБЖУ. Поля свободного текста старого `nextPlan`
  сохранены для совместимости данных, но не отображаются тренеру.
- `trainerDraft.responseGenerated` отмечает отдельный шаг формирования ответа.
  Отправка через UI без этого шага блокируется; правки плана сбрасывают флаг.
  Для сформированного структурированного ответа комментарий может быть пустым.
- `trainerDraft.planAccepted` разрешает формирование ответа только после «Принять».
  Открытие редактора или изменение параметров сбрасывает принятие и сформированный
  ответ, но сохраняет ручные правки и комментарий. `editingBlocks` задаёт доступные
  для редактирования тренировки и питание без перехода на другие экраны.
- `resolution`: время, решение, выбранные рекомендации, структурированные
  `changes`, `nextPlan` с датой действия и копией плана, отправленная `feedback`.
  После закрытия не переписывается.
- Для нового ответа `resolution.delivery` фиксирует полный состав передачи,
  включая комментарии обеих сторон; `changes` поддерживает вес, подходы/повторы
  и питание. Старые закрытые отчёты не мигрируют задним числом.

Состояние определяется наличием полей, а не независимым изменяемым статусом:
`expected` → `submitted` → `reviewed`. Просрочка — вычисляемый признак ожидания.
Повторная отправка/закрытие возвращают существующий результат без дубликата памяти.

Снимок содержит цель/анкету, исторический план, записи периода и предыдущих семи
дней, пять замеров, медиа и прошлое решение. Пропуски остаются отсутствием данных.
Тренировки считаются по уникальным запланированным занятиям с результатом.
Питание: среднее соответствие калорий целевым значениям по последней записи
каждого заполненного дня (`max(0, 100 − |факт − цель| / цель × 100)`), рядом
обязательно показано число дней; отсутствие записи не означает соблюдение.
Вес: последний замер внутри периода относительно последнего до его начала.
Сон/шаги используются только при наличии датированных `activityEntries`.

Период по умолчанию — воскресенье–суббота, отчёт в воскресенье до 18:00
Europe/Moscow. Отправка доступна после окончания периода, не только после
наступления дедлайна. Ожидаемый период не попадает в badge. После первого
созданного периода пропущенные недели догружаются при следующем открытии.
Расписание следующих периодов изменяется отдельно; старые даты сохраняются.

Следующий план фиксируется для начала нового периода. При поздней проверке
изменение переносится на следующую границу недели, не переписывая уже идущую.
Старый отчёт не может заменить более новое решение для той же будущей недели.
Следующий снимок включает предыдущее решение и приоритет для сравнения результата.

## Подключение боевой версии

Сохранить контракт и разделение интерфейсов. Текущий адаптер имеет синхронные
методы `clients`, `client`, `schedule`, `cycles`, `plan`, `save`, `complete`.
Для Supabase потребуются асинхронная загрузка/команды и обновление локальной
модели после серверного подтверждения — это не замена одного URL.

Серверная реализация должна обеспечивать:

1. Проверку Telegram initData на сервере, авторизацию и действующую связь
   тренер–клиент; RLS/проверки доступа. Локальный ID не является авторизацией.
2. Уникальность пары отношений и периода, серверное время/часовой пояс,
   допустимые переходы статусов и версионирование команд для конфликтов.
3. Агрегацию из настоящих тренировок, питания, веса, пяти замеров и истории
   назначений. Клиент не должен присылать доверенный «готовый» снимок фактов.
4. Неизменяемые снимки и архив; отдельное хранение слов клиента, AI-анализа
   с версией модели и окончательного решения тренера.
5. Атомарную транзакцию закрытия: решение + следующий план + память + outbox
   уведомления. Идемпотентные команды и повторы без двойной отправки.
6. Серверный AI-вызов с ключом вне браузера, проверку структурированных действий,
   состояния анализа/ошибки/повтора. Никаких автоматических назначений без тренера.
7. Приватные медиа и права доступа, реальную клиентскую точку входа в отчёт,
   синхронизацию статусов между аккаунтами и уведомления.

SQL и код Supabase здесь намеренно не добавлены. Их подготовить отдельно для
вставки пользователем после согласования существующей схемы и функций.

Проверка: `node --test tests/*.test.cjs`.
